# Этап 5 — согласование программы

21.09.2026. Основной сценарий работает с **изолированным mock API**. Реальный AI и серверное утверждение пока не подключены. Backend повторно проверен через `git fetch origin repeat-center`: commit `12bfd8579e65799117187445bd8fca508af0c43b` не изменился. Backend-файлы не редактировались.

## Проверка вручную

В `frontend/` выполнить `npm run dev:mock`, открыть `http://127.0.0.1:3000`. Вход: `student@example.test` / `Repeat123`.

1. Создать цель, ответить на интервью, сформировать программу.
2. Открыть «Проверить программу». Проверить параметры, темы, источники и ограничения.
3. Выбрать подсказку или написать запрос. Отправить предложение, открыть сравнение «Было / Станет».
4. Применить или отклонить предложение. До применения версия программы остаётся прежней. После reload отправленное предложение восстанавливается.
5. Нажать «Согласовать программу», подтвердить параметры и существующие пробелы в материалах.
6. После ответа mock API появляется экран готовности и один активный курс в кабинете. Утверждённая программа доступна из карточки курса. Прохождение обучения относится к этапу 6.

Маршрут: `/app/plans/:id/review`. Прямая ссылка защищена сессией; путь сохранён для возврата после входа и настроен в production preview.

## Что реализовано

- Просмотр параметров программы, последовательности тем, материалов и статуса источников. Отсутствие проверенного источника явно обозначено; фиктивные ссылки не подставляются.
- Предложение изменений отдельно от текущей программы. Сравнение параметров, добавленных/удалённых тем и изменённых источников; текст отображается безопасно через React.
- Применение и отклонение по ID предложения и ожидаемой версии. Устаревшее предложение после обновления можно отклонить, но нельзя применить.
- Сохранение предложений и утверждённого трека на стороне mock API, отдельное хранилище для каждой демонстрационной учётной записи.
- Повтор мутации с тем же ключом после потерянного ответа. Ключ привязан к содержимому операции; повторное использование для другого payload отклоняется. После успешного ответа новое действие получает новый ключ.
- Подтверждение параметров и пробелов источников перед утверждением. Серверная имитация повторно проверяет эти условия; наличие неприменённого предложения блокирует утверждение.
- Активный трек создаёт обработчик API; клиент обновляет Query cache только по ответу. После reload результат читается с API. Утверждённый план исключается из списка черновиков; повтор генерации для него блокируется.
- Защита несохранённого запроса при переходе и закрытии вкладки. Конфликт не стирает введённый текст. Ошибки видны внутри активного диалога.

## Предварительный контракт

Эти URL существуют только в режиме MSW и **не являются утверждённым backend-контрактом**. Адаптер возвращает `503 REVIEW_UNAVAILABLE`, если mocks выключены. Production-сборка не содержит MSW.

| Операция | Предварительный запрос |
| --- | --- |
| Чтение | `GET /__preview/plan-reviews/:id` |
| Предложение | `POST /__preview/plan-reviews/:id`, `{ action: "propose", expectedPlanVersion, text, kind }` |
| Применение / отклонение | Тот же POST, `{ action: "apply" | "reject", expectedPlanVersion, proposalId }` |
| Утверждение | Тот же POST, `{ action: "approve", expectedPlanVersion, timezone, acknowledgements: { parameters: true, gaps: boolean } }` |

Все POST требуют `Idempotency-Key`. Ответ `{ data: Review }` содержит `id`, `jobId`, `version`, `program`, `proposal | null`, `track | null`. Схемы ответа проверяются Zod. `409` требует обновить версию и заново проверить предложение; `422` означает неподтверждённые условия; `401` очищает сессию; потерянный ответ после сохранения допускает явный повтор.

В настоящем backend найден `POST /plans/{plan_id}/approve`, но нет полного чтения программы и маршрутов proposal/diff/apply/reject. Наличие `PlanChangeRequestBody` и `PlanApplyBody` в схемах само по себе не делает API доступным. Перед интеграцией нужны согласованные DTO, проверки версий, гарантии идемпотентности, серверные источники и ограничения. Клиентский mock ID интервью пока совпадает с review ID; это не утверждение об идентичности серверных Interview, Plan и Track.

Это адаптация рабочего сценария, не заявление о полном pixel-perfect: размеры текста увеличены относительно мелких подписей макета; содержание зависит от брифа; отсутствующие проверенные источники не изображаются найденными. Контрольные точки, расписание модулей и настоящий поиск/замена источника ожидают серверных данных. Демо-подсказки выполняют детерминированные изменения (нагрузка и срок, форматы, дополнительная практика); свободный текст добавляется как пожелание, а не интерпретируется AI. На экране это обозначено явно.

## Проверки

Результаты финального прогона фиксируются в [матрице совместимости](compatibility-matrix.md). Браузерные сценарии: предложение → reload → применение → утверждение; потерянные ответы apply/approve; конфликты версий и сохранение текста; отклонение и повтор того же запроса; подтверждение пробелов; 320 px и текст 200%; защита несохранённого запроса. Скриншоты — `docs/qa/stage5-*.png`.

Для ручной имитации потери ответа в DevTools можно задать `sessionStorage.setItem('repeat-preview-review-response', 'apply')` или `'approve'` перед действием. Обработчик сначала сохраняет результат, затем один раз возвращает 503. Это инструмент QA, не production-механизм.

Остаются: реальный API/AI, верификация источников, реальные устройства и ассистивные технологии, публикация ветки при наличии Write-доступа. Следующий этап — обучение и база знаний.
