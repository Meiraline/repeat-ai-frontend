## 1. Целевой результат

React-приложение с компонентами Atomic Design и отдельными функциональными модулями. Пользователь проходит путь: вход → настройка → создание цели → генерация и согласование плана → обучение → проверка знаний → получение диплома.

В состав планирования также входят лендинг, кабинет, база знаний, AI-репетитор, настройки, тарифы и системные состояния из Figma. Наличие экрана в дизайне не подтверждает наличие готового API.

Каждый сценарий проходит два независимых рубежа: «готов с имитацией API» и «проверен с реальным API». Второй нельзя отмечать на основании первого.

Маркетплейс авторских курсов, кабинет автора, социальная сеть, desktop-приложение и локальное файловое хранилище из большого DOCX не включаются автоматически. Их добавление требует отдельной задачи.

## 2. Как вести план

- Статусы задач: `не начато`, `в работе`, `готово с mocks`, `готово с API`, `заблокировано`.
- Для блокировки указывать конкретную зависимость и продолжать независимые задачи.
- Каждый этап заканчивается работающим проверяемым результатом, а не только созданием файлов.
- Адаптацию, доступность и обработку ошибок делать внутри этапа. Финальная проверка выявляет регрессии, а не впервые добавляет мобильную версию.
- Сроки оценивать после инвентаризации экранов и подтверждения готовности API; сейчас календарные обещания не фиксируются.
- Статусы поддерживать в рабочем списке `docs/implementation-status.md`, который создаётся на этапе 0.

## 4. Работа с бэкенд-разработчиком

| До сценария | Что должно быть определено |
| --- | --- |
| Авторизация | Сессия, cookie/token, восстановление, истечение, CORS/CSRF при необходимости |
| Генерация | Идентификатор задания, статусы, ошибки, повтор, идемпотентность |
| Правки плана | Версия, diff/proposal, подтверждение, конфликт изменений |
| Обучение | Структура трека, прогресс, блокировки, источники |
| Репетитор | Контекст, история, сообщения, протокол ответа и повторы |
| Оценивание | Попытки, сроки, сохранение, сдача, проверка, окончательные результаты |
| Файлы и диплом | Форматы, ограничения, временные ссылки, скачивание |
| Тарифы | Права, checkout, статус подписки, отмена, подтверждение оплаты |

Изменения контракта отражать одновременно в типах, адаптерах, mock handlers и интеграционных проверках. Не отправлять сообщения бэкенд-разработчику самостоятельно без поручения пользователя.

## 5. Готовность отдельного экрана

- [ ] Есть соответствие узлу Figma и переиспользуются общие компоненты.
- [ ] Работают действие пользователя и предусмотренные переходы.
- [ ] Есть применимые loading, empty, error, success и disabled-состояния.
- [ ] Экран адаптирован по связанному плану и управляется клавиатурой.
- [ ] Длинные данные и увеличение текста не ломают компоновку.
- [ ] Пройдены проверки, соответствующие изменению; их результаты записаны.
- [ ] Отдельно указан статус mocks и реального API.
