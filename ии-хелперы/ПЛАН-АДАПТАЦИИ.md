# План адаптации и браузерной совместимости repeat.ai

Дата: 20.09.2026. Статус: правила и план проверок, а не отчёт об уже протестированном приложении.

Применять совместно с [правилами разработки](ПРАВИЛА-РАЗРАБОТКИ.md) и [планом разработки](ПЛАН-РАЗРАБОТКИ.md).

## 1. Что считаем корректной работой

На поддерживаемом устройстве пользователь может пройти все включённые в выпуск основные сценарии: прочитать содержимое, заполнить форму, открыть меню, учиться, общаться с репетитором и отправить работу. Существенная информация и действия не исчезают при смене ширины, масштаба или способа ввода.

Обеспечиваем поддержку по явной матрице ниже. Нельзя обещать проверенную работу во всех существующих браузерах, старых WebView, телевизорах и носимых устройствах. За пределами матрицы сохраняем базовую работоспособность, где это возможно, но не обозначаем непроверенное окружение как поддержанное.

Desktop Figma задаёт визуальный ориентир. Если мобильного макета нет, адаптация строится по этим правилам и фиксируется как принятое проектное решение.

## 3. Размеры и точки перестроения

Все значения ниже — ширина viewport в **CSS px**, а не физические пиксели дисплея. Плотность DPR влияет на чёткость assets, но не выбирает desktop или mobile-компоновку.

Поддерживаем основной поток от 320 CSS px и непрерывное изменение ширины. 2560 px — контрольная точка широкого экрана, не верхний предел страницы.

| Диапазон | Базовое поведение |
| --- | --- |
| 320–479 | Одна колонка, компактные отступы, полноширинные формы |
| 480–767 | Одна основная колонка; небольшие карточки могут размещаться рядом при достаточной ширине |
| 768–1023 | Одна или две колонки по содержимому; навигация в выдвижной панели |
| 1024–1279 | Компактная desktop-компоновка; второстепенная боковая панель сворачивается |
| 1280–1599 | Полная desktop-компоновка при достаточной ширине центрального содержимого |
| 1600 и шире | Ограниченные по ширине контейнеры; свободное место не растягивает текст и формы |

Начальные точки media queries: 30rem, 48rem, 64rem, 80rem и 100rem (при исходном размере 16 px соответствуют 480, 768, 1024, 1280 и 1600 px). Это проектная сетка, а не определения моделей устройств. Дополнительную точку вводить, когда ломается конкретная композиция, с пояснением причины.

CSS писать от простой узкой компоновки к расширенной. Сначала изучать desktop-макет, но не строить мобильную версию уменьшением масштаба готовой desktop-страницы. Гибкие сетки, media queries и корректный viewport — основа responsive-подхода. [MDN: Responsive design](https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/CSS_layout/Responsive_Design)

## 4. Правила контейнеров и CSS

- Установить viewport: `width=device-width, initial-scale=1`. При использовании safe area добавить `viewport-fit=cover` и соответствующие отступы.
- Не задавать `user-scalable=no` и ограничения максимального масштаба.
- Использовать `box-sizing: border-box`, Grid/Flexbox, `minmax(0, 1fr)` и `min-inline-size: 0` в сжимаемых областях.
- Ширина формы: `100%` в пределах её max-width; содержимое не должно выходить за доступную область.
- Начальные боковые отступы: 16 px на узком экране, 24 px на среднем, 32 px на широком; уточнять по токенам и конкретному макету.
- Для чтения ограничивать длину строки примерно 60–75 символами, сохраняя доступную ширину на телефоне. Это проектный ориентир, не обязательный размер всех блоков.
- Не закреплять высоту текстовых карточек и форм, если содержимое может увеличиваться. Равную высоту карточек обеспечивать сеткой.
- Не использовать `overflow-x: hidden` на всей странице, чтобы скрыть дефект. Исправлять переполнение в его источнике.
- Не масштабировать весь интерфейс через `transform: scale()` или CSS `zoom`.
- Не назначать всему приложению `min-width: 1024px` или другую desktop-ширину.
- Не определять компоновку по user agent, названию устройства или `screen.width`.
- Использовать CSS для визуального перестроения. JS `matchMedia` вводить лишь когда меняется поведение, с очисткой подписок и сохранением состояния.
- Не делать две одновременно смонтированные копии формы или чата для mobile/desktop: это дублирует ID, запросы и состояние.
- Breakpoints документировать централизованно. Обычный `var(--breakpoint)` не работает как значение условия стандартного `@media`; использовать согласованные литералы либо настроенное преобразование на этапе сборки.
- Container queries применять для компонентов, зависящих от своей области, после проверки поддержки. Базовая компоновка должна оставаться usable без улучшения.

## 5. Как перестраивать экраны repeat.ai

| Элемент / сценарий | Широкий экран | Узкий экран |
| --- | --- | --- |
| Навигация кабинета | Боковая панель | Кнопка меню и выдвижная панель с теми же разделами |
| Вход и регистрация | Форма и брендовая иллюстрация | Форма на доступную ширину; декоративную иллюстрацию можно убрать |
| Онбординг и интервью | Шаги и вспомогательная область рядом | Один основной шаг, прогресс сверху, помощь раскрывается |
| Кабинет / программы | Сетка карточек | Одна колонка; фильтры открываются отдельной панелью |
| Создание плана | Форма и резюме цели рядом | Последовательные секции, резюме доступно до отправки |
| Генерация | Этапы и детали рядом | Вертикальный список этапов, раскрываемые детали |
| Сравнение плана | Старое и новое рядом | Последовательные блоки с явными подписями и выделенными изменениями |
| Roadmap | Пространственная карта при наличии макета | Последовательный список модулей и тем с зависимостями и статусами |
| Учебная тема | Материал, навигация и помощь рядом | Материал первым; навигация и помощь через вкладки/панели |
| База знаний | Список, детали и фильтры | Список → экран детали; возврат сохраняет фильтр и позицию |
| AI-репетитор | Панель или самостоятельный экран | Полноценная доступная область чата с видимым вводом |
| Экзамен | Навигация вопросов и рабочая область | Вопрос и действия в одной колонке; навигация раскрывается |
| Учебный проект | Требования и отправка рядом | Требования, редактор и отправка последовательно |
| Диплом | Предпросмотр и действия рядом | Вписанный предпросмотр, открытие полного файла и скачивание |
| Настройки | Меню разделов и форма | Выбор раздела и одна основная форма |
| Тарифы | Карточки или сравнение колонками | Карточки последовательно; характеристики и условия остаются доступны |
| Лендинг | Несколько колонок и широкие композиции | Смысловой порядок секций, адаптивные изображения, доступный CTA |

Скрывать можно декоративное или дублирующее содержимое. Основные действия, цены, ошибки, критерии сдачи и условия доступа нельзя убирать ради компактности. Перетаскивание, если оно нужно, должно иметь альтернативу кнопками или меню.

Для действительно двумерного roadmap разрешён отдельный контейнер перемещения, но пользователь должен иметь эквивалентное доступное представление списком. Не превращать всю страницу в бесконечную горизонтальную прокрутку.

## 6. Высота экрана, клавиатура и панели

- Проверять не только ширину, но и низкие окна: ноутбук, landscape телефона, split screen планшета.
- Для обычных страниц предпочитать естественную высоту документа. Не назначать всем экранам фиксированный `height: 100vh`.
- Для оболочки чата использовать цепочку flex/grid с корректным `min-height: 0` и выделенной прокруткой истории.
- Если нужна высота viewport, предусмотреть fallback и осознанно выбрать `svh` или `dvh`; динамическая единица может менять размер при движении браузерных панелей. [MDN: viewport units](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/length)
- `100dvh` само по себе не является гарантией корректной работы экранной клавиатуры. Проверять фокус, прокрутку и панель ввода на реальных телефонах; Visual Viewport API применять только при подтверждённой необходимости.
- Fixed/sticky-действия не должны перекрывать последнее поле, ошибку или сфокусированную кнопку. Резервировать место и учитывать `env(safe-area-inset-bottom)`.
- На малой высоте превращать диалог в прокручиваемую область, сохранять доступ к заголовку, закрытию и основному действию.
- При открытии модального меню блокировать фоновое взаимодействие, управлять фокусом; после закрытия возвращать фокус и прежнюю позицию страницы.
- Поворот устройства и изменение ширины не должны сбрасывать ответ, сообщение, текущий вопрос или статус фоновой операции.

## 7. Текст, изображения и сложное содержимое

- Основной текст задавать в rem; не уменьшать корневой размер шрифта ради помещения интерфейса.
- Поля ввода на телефоне проектировать с размером текста не менее 1rem при стандартной основе 16 px; отдельно проверить поведение фокуса в Safari.
- Длинные названия, имена файлов и URL переносить, например через `overflow-wrap: anywhere` там, где это уместно.
- Не обрезать единственную копию важной информации. Для сокращённого текста дать доступ к полному содержимому без обязательного hover.
- Иллюстрации ограничивать шириной контейнера, сохранять пропорции; для разных размеров использовать подходящие исходники, `srcset`/`sizes` при необходимости.
- Указывать размеры или aspect-ratio изображения для устойчивой компоновки. Иконкам задавать явные размеры.
- `object-fit: cover` использовать для допускающих обрезку обложек; диплом, схема или обучающий скриншот должны оставаться доступны целиком.
- Для тяжёлой иллюстрации выбирать оптимизированный формат с подходящим fallback. Не загружать огромный исходник на телефон без необходимости.
- Отложенно загружать изображения ниже первого экрана; ключевую иллюстрацию первого экрана не задерживать без причины.
- Таблицы данных, код и формулы могут иметь собственную горизонтальную прокрутку с понятным доступом с клавиатуры. Обычный текст и заголовки остаются в ширине страницы.
- Таблицы, где сравнение не требует колонок, адаптировать в подписанные записи. При сохранении таблицы не терять заголовки и семантику.
- Видео и embeds вписывать в контейнер; оставлять доступными управление, субтитры и полноэкранный режим, если они предусмотрены контентом.

## 8. Масштаб, ввод и доступность

- Проверять увеличение текста до 200% без потери содержимого и функций. [W3C: Resize Text](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html)
- Проверять reflow на 320 CSS px и при 400% масштабе окна исходной шириной 1280 CSS px. Исключения для двумерных данных не распространять на всю страницу. [W3C: Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)
- Проектный размер зоны нажатия отдельной кнопки — желательно не менее 44×44 CSS px; обеспечить расстояние между соседними действиями. WCAG 2.2 AA использует минимум 24×24 CSS px с оговорёнными исключениями; 44×44 здесь — более удобный проектный ориентир. [W3C: Target Size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)
- Все основные действия доступны мышью, touch и клавиатурой. Hover не должен быть единственным способом открыть действие или объяснение.
- `hover` и `pointer` media features использовать для улучшений, сохраняя работу на гибридных устройствах.
- Визуальный порядок должен соответствовать логичному порядку DOM и Tab. Не переставлять блоки CSS так, чтобы клавиатура двигалась непредсказуемо.
- Сообщать об ошибках формы рядом с полем; уведомления о важных изменениях делать доступными для screen reader. Не озвучивать каждый токен ответа AI как отдельное срочное сообщение.
- Проверять reduced motion, системный повышенный контраст и видимость фокуса. Не удалять outline без полноценной замены.
- Для Windows провести проверку с NVDA, для Apple — с VoiceOver на ключевых формах и навигации, когда доступны соответствующие среды.

Это набор критериев проекта, а не заявление о полной сертификации WCAG.

## 9. Совместимость CSS, JavaScript и браузерных API

- Проверять поддержку новых возможностей по целевой матрице до их использования в критическом пути.
- Сначала задавать базовый рабочий стиль, затем улучшение через `@supports`. Например, отсутствие размытия фона не должно делать карточку прозрачной и нечитаемой. [MDN: @supports](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@supports)
- Выбирать совместимые зависимости; проверять формы, dialog/popover, sticky, прокрутку и rich text в разных движках.
- Настроить `build.target` и при необходимости CSS target под фактические версии. Наличие Browserslist само по себе не подтверждает, что все инструменты используют одинаковую цель.
- Трансформация синтаксиса Vite не добавляет автоматически все отсутствующие браузерные API. Polyfill подключать адресно и только при необходимости. [Vite: Browser Compatibility](https://vite.dev/guide/build.html#browser-compatibility)
- Clipboard, share, fullscreen, файловый доступ и другие необязательные API проверять по наличию возможности и обрабатывать отказ разрешения.
- Для неподдерживаемого share давать обычную ссылку/скачивание; для clipboard — доступный для выделения текст.
- Не делать основной учебный сценарий зависимым от File System Access API или установки PWA.
- Ошибка storage, запрет cookies или приватный режим должны давать понятное восстановимое состояние. Не терять доступ к публичной части из-за необязательного хранилища.
- Использовать HTTPS в тестовом окружении интеграции и production; отдельно проверить cookie/session и скачивание файлов в Safari.
- После возврата из фона обновлять серверный статус экзамена и генерации. Не полагаться на точность фонового JS-таймера.
- После разрыва сети не повторять автоматически сдачу работы или оплату без согласованной идемпотентности.

## 10. Контрольные размеры

Размеры приведены в CSS px; это тестовые viewport, а не утверждение о точных параметрах конкретной модели телефона.

| Профиль | Размеры для проверки |
| --- | --- |
| Минимальная ширина | 320×568 |
| Телефоны | 360×800, 390×844, 430×932 |
| Телефон landscape | 844×390 |
| Планшеты | 768×1024, 820×1180, 1024×768 |
| Небольшой ноутбук | 1280×720, 1366×768 |
| Основной desktop | 1440×900, 1920×1080 |
| Широкий монитор | 2560×1440 |
| Split screen | Произвольная ширина 500–900, проверка непрерывным изменением |

Дополнительно проверять каждую точку перестроения на 1 CSS px до и после порога. Это выявляет наложение правил. Для растровых assets выборочно проверять DPR 1, 2 и 3; для Windows — масштаб ОС 125% и 150% с фиксацией фактического viewport.

## 11. Автоматические и ручные проверки

### На каждом компоненте и экране

1. Проверить desktop-макет и узкую компоновку.
2. Проверить непрерывное изменение ширины и длинный контент.
3. Проверить применимые loading/empty/error/success и открытые меню/диалоги.
4. Проверить клавиатуру, touch-цели, увеличение текста и отсутствие перекрытий.
5. Запустить затронутые проверки; не повторять весь набор без необходимости.

### Автоматизация

- Playwright: проекты Chromium, Firefox и WebKit для основных сценариев.
- Для ключевых шаблонов — проверки на 320, 390, 768, 1280 и 1440 CSS px; остальные контрольные размеры выбирать по изменённой области.
- Проверять отсутствие горизонтального переполнения документа; отдельно разрешать явно определённые контейнеры таблиц/кода/карт.
- Делать контрольные снимки основных шаблонов при стабильных шрифтах и данных; не утверждать обновление эталонов автоматически при любом отличии.
- Проверять сохранение состояния при resize и повороте, открытие вложенного URL и восстановление после ошибки сети.
- Эмуляция позволяет задать viewport, touch, DPR и другие параметры, но не доказывает работу на физическом устройстве. [Playwright: Emulation](https://playwright.dev/docs/emulation)
- Playwright WebKit не является установленным Safari; стабильные брендовые браузеры и нужные версии проверяются отдельно. [Playwright: Browsers](https://playwright.dev/docs/browsers)

### Перед выпуском

- Проверить production-сборку во всех обязательных строках зафиксированной браузерной матрицы.
- Реальный iPhone/Safari: вход, экранная клавиатура, чат, экзамен, диалог и скачивание диплома.
- Реальный Android/Chrome: тот же путь, системная кнопка «Назад», поворот, медленная сеть и возврат из фона.
- Планшет: обе ориентации и split screen; desktop: низкое окно, zoom и клавиатура.
- Проверить основной путь с реальным API, а не только на fixtures.
- Если нужное устройство или версия недоступны, записать «не проверено» и организовать такую проверку до заявления о полной поддержке матрицы. Допустим сервис реальных устройств; простая эмуляция не заменяет этот результат.

## 12. Порядок внедрения адаптации

| Когда | Что сделать | Условие завершения |
| --- | --- | --- |
| Инвентаризация | Зафиксировать матрицу и мобильные решения | Для каждого шаблона понятно перестроение |
| Основа приложения | Viewport, reset, контейнеры, targets | Тестовая страница не переполняется на 320 px |
| Дизайн-система | Гибкие компоненты, состояния, фокус | Компоненты выдерживают длинный текст и увеличение |
| Каждый функциональный этап | Адаптировать реальные экраны и overlays | Основной сценарий работает на узком и широком экране |
| Интеграция | Проверить реальные данные, сеть, сессии и файлы | Поведение не зависит от идеальных fixtures |
| Подготовка выпуска | Выполнить матрицу браузеров и устройств | Нет блокирующих дефектов, есть фактический отчёт |
| После выпуска | Пересматривать матрицу по аналитике и новым версиям | Изменённая поддержка подтверждена проверками |

## 13. Критерии готовности адаптации

- [ ] На 320 CSS px нет горизонтальной прокрутки всей страницы и потери обязательных действий.
- [ ] На широком мониторе формы и текст сохраняют разумную ширину.
- [ ] Нет наложений на промежуточных ширинах, при увеличении текста и малой высоте окна.
- [ ] Клавиатура телефона не делает отправку формы или сообщения недоступной.
- [ ] Модальные окна, меню и боковые панели доступны с клавиатуры и корректно закрываются.
- [ ] Данные формы, экзамена и чата сохраняются при перестроении интерфейса.
- [ ] Rich text, изображения, код, таблицы и roadmap имеют доступное представление.
- [ ] Критические возможности имеют fallback или понятный путь восстановления.
- [ ] Основные сценарии подтверждены на выбранных браузерах и реальных устройствах.
- [ ] В отчёте указаны реальные версии и результаты, оставшиеся ограничения не скрыты.

Внешний вид может немного отличаться из-за системных шрифтов и рендеринга движка. Потеря функций, текста, фокуса или доступности основного действия считается дефектом, а не допустимым визуальным отличием.
